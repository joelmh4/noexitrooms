Las tablas una a una

usuarios

Obligatoria

Todas las personas que entran en la web. El rol decide qué puede hacer cada una.

idPKINTIdentificador
emailÚNICOVARCHAR(150)No puede haber dos cuentas con el mismo email
hash_contrasenaVARCHAR(255)Hash bcrypt, nunca la contraseña
rolENUMcliente por defecto; solo el admin lo cambia
activoBOOLEANPara bloquear una cuenta sin borrarla

salas

CRUD temático

Las salas del catálogo. Es la entidad propia del negocio que pide el enunciado.

nombre, slugÚNICOVARCHAREl slug forma la URL: /salas/operacion-david
dificultadTINYINTDe 1 a 5, comprobado con CHECK
jugadores_min, jugadores_maxTINYINTCHECK: máximo ≥ mínimo
precio_personaDECIMAL(6,2)Precio orientativo, sin pagos reales
lema, edad_minimaVARCHAR, TINYINTLema de la tarjeta y edad mínima (0 = sin mínimo)
pruebasTEXTPruebas de la sala que salen en su ficha, una por línea
activaBOOLEAN"Eliminar" desactiva si ya tiene tickets

tickets

Obligatoria

Cada consulta o incidencia. Se relaciona con quién la abre, quién la atiende y, si procede, con una sala o reserva.

cliente_idFK→ usuariosCliente que lo abre; base del control de propiedad
agente_idFK→ usuariosAgente asignado; vacío hasta que el admin lo asigna
categoria_idFK→ categoriasObligatoria
sala_id, reserva_idFK→ salas / reservasOpcionales: de qué sala o partida se habla
prioridadENUMbaja · media · alta
estadoENUMabierto · en_curso · pendiente_cliente · resuelto · cerrado

mensajes

Obligatoria

Las respuestas de la conversación. Guarda quién escribió cada una y cuándo.

ticket_idFK→ ticketsSi se borra el ticket, se borran sus mensajes
autor_idFK→ usuariosCliente, agente o admin
nota_internaBOOLEANMejora: nota que el cliente no ve

historial_estados

Obligatoria

Un registro por cada cambio de estado, para mostrar el historial y poder auditarlo.

autor_idFK→ usuariosQuién hizo el cambio
estado_anteriorENUMVacío en el registro de creación
estado_nuevoENUMEstado nuevo

categorias

Obligatoria

Tipos de consulta que administra el admin. Se desactivan en vez de borrarse.

nombreÚNICOVARCHAR(80)Reservas, Bonos, Grupos, Objetos perdidos, Reclamaciones, Cuenta

reservas

Mejora opcional

Reservas de partida. Es la segunda entidad que se propuso como mejora en la ficha; si no se hace, se quita junto con tickets.reserva_id.

sala_id + fecha_horaÚNICO—Una sala no se puede reservar dos veces a la misma hora
estadoENUMpendiente · confirmada · cancelada

Decisiones de diseño

  • El rol vive en usuarios.rol. Con tres roles fijos no hace falta una tabla aparte, y el backend lo comprueba en cada petición con un middleware.
  • La propiedad se comprueba con tickets.cliente_id. Un cliente solo recibe tickets donde cliente_id es el suyo; un agente, donde agente_id es el suyo. Así se supera la prueba de cambiar el id en la URL.
  • El código visible (NXR-0042) no se guarda. La API lo forma a partir del id ('NXR-' + id con 4 cifras), así nunca se duplica ni se desincroniza.
  • Desactivar en lugar de borrar. Salas y categorías tienen activa y los usuarios activo; las claves foráneas usan RESTRICT para no perder tickets por un borrado.
  • Los datos que el enunciado llama "trazabilidad" están en creado_en, actualizado_en, los mensajes y el historial de estados.
  • Validación doble. La base de datos impide valores imposibles (CHECK, UNIQUE, ENUM) y el backend devuelve el error con un mensaje claro y el código HTTP adecuado (400, 409…).
