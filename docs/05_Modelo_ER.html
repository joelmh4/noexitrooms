Las tablas una a una

Todas las personas que entran en la web. El rol decide qué puede hacer cada una.

emailÚNICOVARCHAR(150)No puede haber dos cuentas con el mismo email
password_hashVARCHAR(255)Hash bcrypt, nunca la contraseña
roleENUMcliente por defecto; solo el admin lo cambia

CRUD temático

Las salas del catálogo. Es la entidad propia del negocio que pide el enunciado.

min_players, max_playersTINYINTCHECK: máximo ≥ mínimo

Decisiones de diseño

  • El rol vive en users.role. Con tres roles fijos no hace falta una tabla aparte, y el backend lo comprueba en cada petición con un middleware.
  • La propiedad se comprueba con tickets.customer_id. Un cliente solo recibe tickets donde customer_id es el suyo; un agente, donde agent_id es el suyo. Así se supera la prueba de cambiar el id en la URL.
  • El código visible (NXR-0042) no se guarda. La API lo forma a partir del id ('NXR-' + id con 4 cifras), así nunca se duplica ni se desincroniza.
  • Desactivar en lugar de borrar. Salas, categorías y usuarios tienen is_active; las claves foráneas usan RESTRICT para no perder tickets por un borrado.
  • Los datos que el enunciado llama "trazabilidad" están en created_at, updated_at, los mensajes y el historial de estados.
  • Validación doble. La base de datos impide valores imposibles (CHECK, UNIQUE, ENUM) y el backend devuelve el error con un mensaje claro y el código HTTP adecuado (400, 409…).
